## ۱. فیلتر محصولات

### سه سطح، و اینکه کدام‌شان id لازم دارد

پاسخِ `GET /api/products/{cuid}/filters` سه لایه دارد؛ سایدبار فقط با لایه‌ی سوم کار دارد:

| در پاسخ | یعنی چه | در سایدبار |
|---|---|---|
| `data[]` | دسته‌ی کلی — الان فقط «مشخصات فنی» | معمولاً نمایش داده نمی‌شود |
| `data[].attributes[]` | گروه: «گرید»، «سایز (قطر)»، «طول شاخه» | **سرتیتر** — از `display_name` |
| `…attributes[].values[]` | گزینه: «A3»، «۱۰۰»، «۱۲ متر» | **چک‌باکس** — برچسب از `display_value`، و **`id` همان چیزی است که می‌فرستید** |

> ⚠️ `filter_categories[]` را برای تیکِ گزینه نفرستید. آن روی *گروه* فیلتر می‌کند،
> یعنی «هر واریانتی که اصلاً گرید دارد» — که تقریباً همه‌شان‌اند. فرستادنِ id یک گزینه
> در آن پارامتر ۴۲۲ می‌گیرد (`exists:attributes,id`).

### قرارداد رسمی

```
GET /api/products/{cuid}/variants?filter_values[]=57&filter_values[]=93&per_page=24
GET /api/products?category=2&filter_values[]=57
```

### ⛔️ شکلِ برچسبی حذف شد — چون هرگز کار نمی‌کرد

این سند قبلاً می‌گفت `?سایز (قطر)=100` «به idِ مقدار ترجمه می‌شود، پس بدون
تغییر فرانت کار می‌کند». **غلط بود.**

تیمِ فرانت روی کاتالوگِ واقعی اندازه‌گیری کرد: هیچ‌کدام از شکل‌های برچسبی چیزی
را محدود نمی‌کردند. علتش این است که آن کد نامِ پارامتر را با `attributes.name`
تطبیق می‌داد، و در کاتالوگِ واقعی `name` نامِ ماشینیِ انگلیسی است (`size`,
`grade`) در حالی که سایدبار `display_name` فارسی را می‌فرستاد.

تستِ ما سبز بود چون سیدرِ نمایشی `name` و `display_name` را یکی می‌گذارد —
یعنی روی داده‌ای می‌گذشت که شکلِ داده‌ی واقعی را نداشت.

مسیر **برداشته شد** نه اینکه روی `display_name` هم سوار شود: مصرف‌کننده‌اش دیگر
وجود ندارد (فرانت به `filter_values[]` مهاجرت کرده)، و مسیری که ادعا می‌کند کار
می‌کند ولی نمی‌کند از نبودنش بدتر است.

### معنای انتخاب چندتایی

```
داخل یک گروه   → OR    (گرید = A3 یا A4)
بین گروه‌ها     → AND   (گرید ∈ {A3,A4}  و  سایز ∈ {100})
```

گروه‌بندی سمتِ سرور و از روی خودِ داده انجام می‌شود؛ شما همان فهرستِ تختِ
`filter_values[]` را می‌فرستید.

### چیپ‌های روی هر واریانت

```json
{
  "attribute_id": 12,
  "name": "گرید",
  "label": "گرید",
  "value": "A3",
  "display_value": "A3",
  "attribute_type": { "name": "technical_specs" }
}
```

### پارامترهای دیگر

| param | مقادیر | روی کدام |
|---|---|---|
| `sort` | `newest` `oldest` `cheapest` `most_expensive` `best_selling` | variants |
| `sort` | `newest` `cheapest` `most_expensive` `most_viewed` `best_selling` | products |
| `per_page` | ۱ تا **۱۰۰** — بیشتر ۴۲۲ | هر دو |
| `category` | id دسته | products |
| `search` | نام و SKU | products |

## ۲. مبالغ حالا بدون اعشار برمی‌گردند

```diff
- "final_amount": "41500.00"
+ "final_amount": "41500"
```

عدد عوض نشده؛ فقط رشته کوتاه‌تر است، و برای ریال دقیق‌تر هم هست.

**کجاها را چک کنید:** `parseFloat`/`Number` و `toLocaleString` بی‌خطرند؛
`.split('.')` یا regex روی اعشار می‌شکند؛ اسنپ‌شات‌ها و mockها به‌روزرسانی لازم دارند.

**فیلدها:** سبد (`price`, `final_price`, `vat_amount`, `total_with_vat`, `total_amount`)،
سفارش (`final_amount`, `partial_payment_amount`, `official_price`, `payment_of_owner`,
`payment_to_supplier`, `payment_to_elite_yar`, `payment_to_reserve`,
`supplier_debt_amount`, `overweight_pending_amount`)، آیتم سفارش (`unit_price`,
`total_price`, `shipping_cost`)، قیمت (`general_price`, `special_price`,
`golden_figure`)، حمل (`flat_cost`, `per_kg_cost`, `per_count_cost`, `shipping_cost`)،
کاربر/بدهی (`debt_balance`, `badge_purchase_amount`, `amount`).

**دست‌نخورده ماندند:** `coupons.amount`، `offers.value`،
`product_variants.discount_value` (دووجهی: درصد **یا** مبلغ ثابت)، هر
`*_rate`/`*_percentage`، و همه‌ی وزن‌ها و مقادیر (سه رقم اعشار).

## ۳. درخت تصمیم پرداخت

`GET /api/checkout/payment-options` **منبع واحد برای بک‌اند و فرانت** است — شاخه را از
همین‌جا بخوانید و خودتان دوباره حساب نکنید.

| شرط | شاخه | اقدام |
|---|---|---|
| `Final ≤ Wallet` | `wallet` (الف) | `POST /checkout/pay` |
| `Final ≤ Wallet + Shaparak` | `gateway` (ب) | **اول کیف پول را شارژ کن**، بعد `POST /checkout/pay` |
| `Final > Wallet + Shaparak` | `reserve` (ج) | `POST /checkout/reserve` |

معیار **توان پرداختِ همین کاربر** است، نه یک آستانه‌ی مبلغیِ سراسری.

> ⚠️ **پول درگاه همیشه اول به کیف پول می‌رود.** `gateway_amount` یک **شارژ** است، نه
> پرداختِ مستقیمِ سفارش. `POST /checkout/pay` در شاخه‌ی ب با ۴۲۲
> `checkout.top_up_wallet_first` رد می‌کند.

> ⚠️ **رزرو یک روشِ پرداختِ دلخواه نیست** — راهِ گریز از ناتوانیِ پرداخت است. فقط در
> شاخه‌ی ج در دسترس است (`reserve_available: true`). در دو شاخه‌ی دیگر
> `POST /checkout/reserve` با ۴۲۲ `checkout.reserve_not_available` رد می‌شود.
>
> **کارتِ «با حضور در بانک» شاخه‌ی ب است، نه ج**: واریز ساتنا/پایا کیف پول را شارژ
> می‌کند، سپس `POST /checkout/pay`. وصل‌کردنش به `/checkout/reserve` یعنی سفارشی که
> باید کامل پرداخت شود فقط بیعانه می‌گیرد و کالا قفل می‌شود.

هر دو اندپوینت `idempotency` + `throttle:financial` دارند و **رکورد سفارش فقط داخلِ
همین‌ها ساخته می‌شود** — پیش از پرداخت هیچ سفارشی وجود ندارد.

`POST /checkout/reserve` وقتی `reserve_warning.show` باشد `confirm_short_window: true`
می‌خواهد، وگرنه ۴۲۲.

## ۴. وضعیت‌های سفارش

هشت وضعیت، و بس:

```
reserved · processing · awaiting_weight_correction · shipped
partially_delivered · delivered · returned_to_origin · cancelled
```

وضعیت‌های حذف‌شده (`pending`, `reserved_extended`, `preparing`, `weighbridge_done`,
`waybill_issued`, `pending_surplus_payment`, `completed`, `failed`) با مهاجرت به
جانشین‌هایشان نگاشت می‌شوند. یک ردیفِ خارج از این هشت‌تا یعنی سفارش از **هر سه تبِ**
«سفارش‌های من» ناپدید می‌شود، چون `current`/`delivered`/`cancelled` دقیقاً همین هشت را
افراز می‌کنند.

ادمین **فقط لغو اجباری** دارد؛ هیچ گذارِ رو‌به‌جلویی ندارد، و لغو اجباری هم
`ticket_id` و `reason` (حداقل ۱۰ نویسه) الزامی می‌خواهد.

## ۵. باسکول: اندپوینت ادمین حذف شد

`POST /admin/orders/{order}/weighbridge` **عمداً** حذف شده. در طراحی جدید نویسنده‌ی
وضعیت «در حال حمل» تأمین‌کننده است: وزن باسکول همراه بارنامه و مشخصات راننده یکجا ثبت
می‌شود.

```
POST /api/profile/orders/{order}/shipments/{shipment}/waybill

{
  "waybill_ref":          "12345",        // الزامی، ≤۱۰۰
  "driver_name":          "…",            // الزامی، ≤۱۵۰
  "driver_national_code": "0012345678",   // اختیاری، دقیقاً ۱۰ رقم
  "driver_mobile":        "09121234567",  // اختیاری، ^09\d{9}$
  "vehicle_plate":        "…",            // الزامی، ≤۳۰
  "vehicle_type":         "…",            // اختیاری
  "actual_weight":        24500,          // الزامی، ≥۱
  "is_final":             true            // «این آخرین محموله بود»
}
```

> ⚠️ کد ملی و موبایلِ راننده **اختیاری‌اند** (بارنامه‌ی کاغذی همیشه هر دو را ندارد) —
> فرم را الزامی نکنید.
>
> ⚠️ `is_final: true` ماشه‌ی **تسویه‌ی مالی نهایی** است و برگشت‌پذیر نیست. در UI باید
> تأییدِ جدا داشته باشد، نه یک چک‌باکسِ ساده کنار بقیه.

## ۶. مواردی که کار فرانت ندارند

- **`GET /api/faq-categories` کار می‌کند** و دسته‌ها را با سؤالاتشان تودرتو در یک
  کوئری برمی‌گرداند. اسلاگ **`purchase`** یک قرارداد است — آکاردئون صفحه‌ی محصول روی
  آن سوار است؛ عوض شود، آن بخش بی‌صدا خالی می‌شود.
- **`/docs/api` و لو رفتنِ دیباگ** پیکربندیِ استیجینگ است نه کد: نگهبانِ داکیومنت وقتی
  محیط `local` باشد کنار می‌رود، و `APP_DEBUG=true` مسیر فایل‌ها را برمی‌گرداند. رفع:
  `APP_ENV=staging`، `APP_DEBUG=false`، و چون مبدأهای `localhost` در CORS به
  `APP_ENV === 'local'` گره خورده‌اند،
  `CORS_EXTRA_ORIGINS=http://localhost:3000,http://localhost:5173,http://localhost:5174`.
- **ویرایش دسته‌ی سؤالات متداول** دیگر ۴۲۲ «اسلاگ تکراری» نمی‌دهد.
- **شش پیامِ گزارش‌های ادمین** دیگر کلیدِ خام برنمی‌گردانند.
- **واریز با کد ملیِ مشترک** حالا برای تأیید دستی پارک می‌شود — صفِ ادمین ممکن است
  ردیفِ بیشتری داشته باشد.

## ۷. کارهای باز

- **درگاه پرداخت لایسنس ندارد.** مسیر تأیید تراکنش fail-safe است و هرگز مبلغی را جعلی
  تأیید نمی‌کند؛ پس روی استیجینگ پرداختِ واقعی تست نمی‌شود.
- **نظرسنجی محصول و ثبت نظر** پشتِ فیچرفلگ خاموش‌اند و روتشان ثبت نمی‌شود — پاسخ ۴۰۴
  است نه ۴۰۳.
- **قرارداد فیلترِ برچسبی موقتی است** و پس از مهاجرت برداشته می‌شود.
